m3ter bill → Revenue Cloud sync

How a bill that m3ter has already rated becomes Revenue Cloud's usage chain — a UsageSummary, a UsageRatableSummary and the UsageBillingPeriodItem (liable summary) that the invoice run reads — per usage line, so that Generate Invoices adds the usage to the same bill as the flat charge. The Python port of the m3sh Usage Data workflow set, built as the same Lego as ordersync: independent steps run by one parent script.

m3terPython syncSalesforce / Revenue Cloudsupportingopen decision

1. Overview

What it does

Given a bill in m3ter, the sync reads the bill and its USAGE line items once, resolves each line back to the Salesforce entitlement it was priced for (the pricing_<TUE Id> trail the order sync left behind), and then — per line, in this order — finds or creates the UsageSummary, the UsageRatableSummary and the UsageBillingPeriodItem for that bucket and period, links the three together, and leaves the liable summary at the status the invoice run looks for.

The platform's own pipeline (journals → summaries → rating → liable summary, run by the Orchestrate Usage Management flow) is bypassed on purpose: m3ter has already aggregated and rated. Revenue Cloud only needs the answer, in the record it invoices from. Re-running a bill finds everything and changes only the numbers — the same idempotency the m3sh workflows get from their natural-key SOQL, with the per-line state bug fixed.

How it will be run

set -a; source parameters/m3ter.env; set +a
PYTHONPATH=. uv run demoscripts/billsync/sync_bill.py \
    --bill <m3ter bill id> [--dry-run] [--final]

--from-file json/entrust/bills/<bill id>.json   replay a saved snapshot
--account <m3ter account id>                   latest bill for the account
--status new|ready                             override the status policy

By hand first, as sync_order.py is; then the billing.bill.created / billing.bill.updated webhook that fed m3sh posts to a Flask route in webhooks/ calling sync_bill.run(bill_id). m3ter auth from parameters/m3ter.env; Salesforce auth from the local sf CLI session (org alias m3ter). --dry-run performs every lookup and prints every payload. After the sync, the bill is produced in Revenue Cloud, not here: Generate Invoices on the account (or an invoice batch run) picks the liable summaries up.

2. Structure of the Python code

The same contract as ordersync, and the same two bricks reused unchanged: a step is a class with one run(ctx); sync_bill.py builds the context and runs the list; ctx.snapshot is the bill read once up front, ctx.state is what each step resolved or wrote, keyed per line so that nothing from line 1 can leak into line 2 (the m3sh bug). Only ReadBill and ResolveAccount touch m3ter; steps 3–8 touch Salesforce, each through create_or_pretend() / update_or_pretend(), so a dry run is one flag.

The run, step by step

  1. ReadBill — resolves --bill (an m3ter bill id, or the latest bill of --account), reads the Bill header (account, bill date, service period, currency, locked), its line items filtered to lineItemType = USAGE, and for each line the Pricing (code, aggregation, segment) and the AccountPlan it bills under. Writes the snapshot. Warns if the bill is not locked and --final was not given.
  2. ResolveAccount — reverse mapping m3ter Account → Salesforce Account.Id. The m3sh workflow had no FALSE branch here and ended silently; the port raises.
  3. ResolveLines — per line, the TUE Id from the pricing (pricing_<TUE Id>, or the mapping); then one TransactionUsageEntitlement query for all of them (AssetId, UsageResourceId, EntitlementUomId, GrantBindingTargetId, AccountId) and one UsageEntitlementBucket query for the child buckets (Parent.Type = 'UsageEntitlementBucket', TransactionUsageEntitlementId IN (…)), reading BucketBalanceUomId off the result rather than filtering on it. A line with no TUE, no asset or no child bucket stops the run before anything is written.
  4. NetLines — total = line.quantity; overage = the quantity in the priced bands (today all of it: the grants are 0 and no commitment Balance exists); debited = total − overage; amount = line.subtotal; rate = amount / overage (0 if overage is 0). One definition, used by all three objects — the two m3sh halves disagreed about ConsumptionUnits.
  5. EnsureUsageSummaries — per line: SELECT Id, RatableSummaryId, LiableSummaryId FROM UsageSummary WHERE AccountId = … AND AssetId = … AND StartDateTime = … AND EndDateTime = … AND UsageEntitlementBucketId = …; several hits is an error, not "last wins"; none → create with Status = New; one → update the numbers with no Status in the payload, and remember the two back-link ids. Per line — ctx.state.summaries[line.id].
  6. EnsureRatableSummaries — per line: the summary's RatableSummaryId, else create; update otherwise, again without Status.
  7. EnsureLiableSummaries — per line: the summary's LiableSummaryId, else create with Status = policy.status_for(bill); otherwise update the quantities and amount, and set Status = ReadyForInvoicing only when the bill has become final since the last run. A liable summary already Invoiced is left alone and reported.
  8. LinkAndBucket — for a summary created this run, write RatableSummaryId and LiableSummaryId onto it (the only link between the three; it lives on the summary). With --bucket, also set the child bucket's BucketBalance = total and ConsumedEntitlement = debited, as m3sh did; off by default because it bypasses Revenue Cloud's own drawdown and Acme's buckets hold no entitlement.

Then, in Revenue Cloud: Generate Invoices on the account (draft first). The pass criterion is six usage InvoiceLine rows on the same invoice as the flat line, each with IsUsageBasedInvoiceLine = true, the resource's product, the m3ter quantity and amount, the service period as its dates, and a BillingPeriodItem whose RelatedUsageBillPeriodItemId is the liable summary the sync wrote.

4. Decisions, and what is still open

Write the liable summary, not the journals

The invoice run reads only UsageBillingPeriodItem; the summaries behind it are for Revenue Cloud's own pipeline, which this org never runs (the scheduled flow is active but has no cron job). The sync writes all three anyway — the summary is the natural key and carries the only back-links, and the ratable summary is where the rate is visible — but the liable summary is the one that matters, so a first pass can key on bucket + period and write it alone.

One definition of the quantities

m3sh's two halves disagreed: Python posted ConsumptionUnits = quantity and OverageUnits = final, the workflow then set DebitedUnits = ConsumptionUnits and added the two. NetLines defines total, overage and debited once; today overage is the whole quantity because every grant is zero.

State per line

Every ctx.state entry is a dict keyed by line item id. The m3sh entry point reused one sfUsageSummary across the loop, so a found summary on line 1 made lines 2–6 update line 1's ratable and liable summaries.

The join is the pricing

m3sh keyed lines through AccountPlan.customFields.TUEId — one AccountPlan per resource. Document Check has six TUEs on one AccountPlan, so the key moves to the Pricing the order sync creates per TUE (pricing_<TUE Id> + the mapping); the bill line's pricingId is the join.

Dates

The inverse of the order sync: m3ter's exclusive end (midnight) becomes Revenue Cloud's inclusive end (23:59:59) by subtracting one second, on all three objects. The platform's own buckets and entitlements end at 23:59:59, and the liable summary's dates become the invoice line's.

Revenue Cloud rules to remember

  • A usage billing schedule is invoiced only when a liable summary is ReadyForInvoicing and the liable summary, bucket and entitlement account share the asset as GrantBindingTargetId and the schedule and bucket name the same resource. Target date and billing-period count do not gate it.
  • UsageBillingPeriodItem.Status has no default; UsageResourceId and UsageEntitlementAccountId are read-only and come from the bucket.
  • Posting an invoice sets the liable summary to Invoiced; voiding reverts it to ReadyForInvoicing; a draft touches nothing — so the first tests are drafts, regenerated at will.
  • Writes to the three objects need the Usage Management Run Time permission set on the integration user; the loader's sf session is an admin, which has it.

Open before the first run decide

  • Parent or child bucket on the liable summary. m3sh used the child; the 20 Oct usage summaries point at the child; the help says only "the bucket". The platform's own run (journals + One Click Orchestrate Usage Flow) will show which bucket its liable summary references. Build to the child, keep it one constant.
  • Status on create. ReadyForInvoicing directly, or New → InProgress → ReadyForInvoicing? Every field is updateable and there is no default, so both are possible; the policy brick decides from the bill's locked state. To test on the first bill.
  • Does a liable summary with no summary behind it invoice? The only link is UsageSummary.LiableSummaryId, on the summary side, so probably yes — which would make a UBPI-only sync legitimate. To test.
  • Which rate the bill used. Order 00000102 carries both the List and the Commit card with none chosen; the order sync priced from the List card. Until the card is chosen at quote time, the m3ter rate and the Revenue Cloud asset rate can disagree, and the invoice will show m3ter's.
  • Billing frequency alignment. Revenue Cloud's usage schedule and the entitlement account are monthly from the 14th (the order start); the m3ter AccountPlan bills on its own cycle. The liable summary's period is whatever m3ter's service period is — the invoice line will show it as such, but the schedule's NextBillingDate stays on the 14th.
