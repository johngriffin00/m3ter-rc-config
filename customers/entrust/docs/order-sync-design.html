Order activation → m3ter sync

How an activated Revenue Cloud order becomes an account, a plan, negotiated pricings and an attached plan in m3ter — the Python port of the m3sh Order Handler workflow set, built as independent steps run by one parent script.

Salesforce / Revenue CloudPython syncm3tersupporting

1. Overview

What it does

Given an activated order, the sync reads the whole order graph out of Salesforce once, then creates in m3ter — in this order — the Account, one bespoke Plan per order line carrying the line's price as a standing charge, one Pricing per usage entitlement carrying the negotiated rate, and the AccountPlan that attaches the plan to the account for the asset's lifecycle.

Every m3ter step looks before it creates: it checks an ExternalMapping keyed on the Salesforce Id, then falls back to the object's code. Re-running an order therefore finds everything and creates nothing — the same guard the m3sh workflows get from ExternalMappingExistsForSystem.

How it is run

Invoked by hand today after activating an order; a Flask route in webhooks/ calling sync_order.run(order_ref) is the planned second front door. 2. Structure of the Python code

Lego, not a script: each step is a class with one run(ctx) method; sync_order.py is the parent that builds the context and runs the list. A step reads what it needs from ctx.snapshot and ctx.state, writes what it found or created back into ctx.state under its own key, and never queries Salesforce itself — the snapshot is read once, up front.

The run, step by step

  1. ReadOrder — resolves --order (8-digit OrderNumber or an Id), then reads Order → Account → Contacts → OrderItems → TransactionUsageEntitlements → Assets → UsageEntitlementBuckets → OrderItemRateCardEntries → AssetRateCardEntries, strips Salesforce's attributes noise and writes json/entrust/orders/<OrderNumber>.json. Warns if the order is not Activated.
  2. EnsureAccount — ExternalMapping.find('Salesforce','Account', AccountId); else an account whose code is the AccountId (adopt it and add the mapping); else create. Mapping key: Salesforce/Account.
  3. EnsurePlans — for each OrderItem: mapping lookup; else by code <product>_<OrderNumber>; else create from the template mapping.py names, bespoke to the account. Mapping key: Salesforce/OrderItem.
  4. EnsurePricings — indexes the rate rows on RATE_CARD by (OrderItemId, resource code); for each TUE: mapping lookup; else resolve aggregation + segment, require a non-null NegotiatedRate, create one pricing on the line's plan. Mapping key: Salesforce/TransactionUsageEntitlement.
  5. EnsureAccountPlans — for each OrderItem: its asset (via the TUEs); mapping lookup; else create the AccountPlan with the asset's lifecycle dates. Mapping key: Salesforce/Asset.

4. Decisions and the rules behind them

Plan per OrderItem, not per Order

An m3ter Plan belongs to one PlanTemplate, which belongs to one Product. An order with two products needs two plans, and each line has its own asset dates. For this catalog every order still yields exactly one plan.

Bespoke plan, plan-level pricings

A negotiated rate in m3ter is a Pricing on a Plan that overrides the PlanTemplate's for the same aggregation and segment. Creating the plan with accountId makes it attachable to that account only, so one customer's rates can never reach another. The template's list-price pricings are untouched. m3sh attaches a shared plan instead — fine at list price, not with negotiated rates. Entrust production uses the same per-contract plan pattern (checks_<opportunityId>).

Dates

Revenue Cloud ends a lifecycle at 23:59:59 of the last day (inclusive); m3ter dates are exclusive. The AccountPlan therefore ends at midnight of the following day — what m3sh does with dateAdd(…, 1, "SECONDS").

m3ter rules to remember

  • Only one active AccountPlan per Product per Account unless the org allows overlapping plans — a renewal must start after the previous AccountPlan ends.
  • A Pricing's segment must be one the aggregation declares; {} is the catch-all.
  • Account.emailAddress is required on create.
  • cumulative: true is tiered pricing, false volume pricing — irrelevant with one band, deliberate once tiers arrive.
