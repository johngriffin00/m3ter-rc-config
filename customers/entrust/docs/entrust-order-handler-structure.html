Entrust Order Handler

How the eight exported m3sh workflows hang together: one entry point, six sub-workflows that share its state, and one stray. Every step below is read from the JSON exports, including the branches your draft stopped before.

Call graph

Three phases, one Order

Phase 1

Setup and Account

  • sfOrder comes from the trigger body.
  • init seeds m3LineItemTypes=[USAGE] and the two TransactionType ids (grant, commit).
  • Account creation looks up the mapping Account → sfOrder.AccountId; hit = load m3 Account, miss = read SF Account, transform, create, map.
Phase 2

Entitlements → AccountPlans

  • SOQL all TransactionUsageEntitlement rows under the Order's OrderItems.
  • Per TUE: read its Asset, build key ProductId#UsageResourceId, look up m3 Product.
  • Hit and planStatus ≠ "NOT" → AccountPlan creation, then product id appended to m3ProductDrawdownIds. Miss → TUE appended to sfTUEnoMatch.
Phase 3

Grants → Balances

  • SOQL OrderItemUsageRsrcGrant (GrantQuantity > 0) under the Order.
  • Per grant: query the Asset, read the ProductUsageGrant, skip if a Balance is already mapped to it.
  • Otherwise branch on UsageModelType (matrix below): build m3Balance, fix endDate, create Balance, map it, post the opening BalanceTransaction, then clone monthly.

All four branches share: accountId=m3AccountId, lineItemTypes=[USAGE], code = ProductUsageGrant.Id + "--", endDate = eoMonth(Asset.LifecycleStartDate) + 1 day (then shaved by hack endDate), mapping ProductUsageGrant → Balance.

What to settle before writing handler.py

  1. Hard-coded product ids in the Grant branch. The Grant Balance's productIds are two static UUIDs (8afbbe85…, 2ee7eaf1…), even though the branch has just looked up m3ProductBalanceId. The Python version should take these from config or use the looked-up product.
  2. Two lists are built and never read. m3ProductDrawdownIds and sfTUEnoMatch are populated in Phase 2 but nothing consumes them. Either they were meant to drive drawdown Balance productIds, or they are logging. Decide which.
  3. hack Balance endDate is a priority trick. Shaving 3/2/1 seconds off the endDate for Hrs/GBs/TOK (0 for USD) makes otherwise identical endDates distinct, which is what m3ter uses to order drawdown across balances. In Python this is one dictionary: {"Hrs":3,"GBs":2,"TOK":1}.
  4. Balance Cloner uses a SOQL LIMIT n as a for-loop. m3sh has no numeric loop, so it queries n TUE rows just to iterate. In Python it is for i in range(nrClones). Check the count: Grant and CommitmentSpend use dateDiff(start, end, MONTHS), so a 12-month Asset yields the original plus 12 clones (13 balances). Confirm whether that is intended or an off-by-one.
  5. The cloner re-posts the same BalanceTransaction. Each clone gets a Tx with the same amount and description as the first balance; the clone's startDate/endDate come from m3BalanceResponse (the saved balance), its name swaps the month word, its code is m3Balance.code + i.
  6. CommitmentQuantity supersedes the Anchor grant. It is the only branch that does not clone and the only one that calls undo Grant Balances, which deletes any Balance on the account whose name contains “Grant” and whose productIds match. Its ListM3terEntity step passes m3Balance.endDate as parent id, which looks like a misconfiguration.
  7. Idempotency comes entirely from external mappings. Account (Account), AccountPlan (TransactionUsageEntitlement and the synthetic m3AccountPlan table keyed accountId#productId) and Balance (ProductUsageGrant) are each checked before creation. The Python handler needs the same lookup table or a local equivalent.
  8. Plan selection is by name. AccountPlan creation lists plans for the product and picks the first whose name contains "(TOK)" or "(USD)" depending on m3Product.customFields.rateCurrency. Inside that loop a second matching plan would try to create a second mapping for the same TUE.
